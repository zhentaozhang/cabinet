# 决策：不加跨请求缓存

结论：**不引入**跨请求的 read model 缓存（`unstable_cache` / 自建 TTL）。
保留现有的「同一请求内去重」（React `cache()`），仅此而已。

下面是做出这个决定的测量数据，不是偏好。

## 测量（真实数据库，20 次迭代，warm）

| 页面 | p50 (ms) | p95 (ms) |
|---|---|---|
| today | 5.3 | 14.5 |
| review | 7.7 | 12.4 |
| cabinet | 4.4 | 7.5 |
| task | 2.0 | 6.0 |
| memory | 1.0 | 1.8 |
| audit | 0.5 | 0.7 |
| shell | 0.4 | 0.7 |
| agent | 0.3 | 0.3 |

复现：`pnpm bench:reads`（`scripts/bench-reads.ts`）。

传输体积（gzip 后，真实登录后的响应）：

| 资源 | 原始 | gzip |
|---|---|---|
| `/` HTML | 140 KB | 18.5 KB |
| `/api/today` | 12.9 KB | — |
| `/api/review` | 24.9 KB | — |

客户端 JS chunk 总计：**900 KB**（清理 zod 之前是 1012 KB，其中 ~400 KB 是
React/Next 运行时，不可压缩）。

## 为什么缓存不划算

1. **能省的时间是个位数毫秒。** 缓存命中最多省掉 0.3–15ms 的服务端时间。
   一次真实的网络往返（哪怕是同机）在 1–5ms 量级，占大头的是 TLS/连接与
   序列化，不是这些查询。
2. **代价是诚实性。** 这个产品的核心承诺是「看到的就是刚刚发生的」——审批、
   预算、审计链、队列状态。为了 5ms 让用户在批准后看到一个旧数字，正好违背
   产品主张。缓存失效点会散落在十几个写路径上，漏一个就是「我明明拒了，它还
   显示待审」。
3. **缓存会让排查变复杂。** 出问题时第一个要排除的变量变成「是不是缓存」，
   而当前的 p95 根本不值得这个代价。

## 什么情况下应重新评估

出现下列任一情况时，这个决定应该被推翻，并按数据重新设计（届时倾向
「按事件版本号缓存 + 写路径递增版本」，而不是按时间 TTL）：

- 任一读模型 p95 超过 50ms（先用 `bench:reads` 定位是查询还是序列化）
- 单用户任务/证据数据量进入数千行量级
- 出现跨用户共享的只读数据（例如公共模板、公开的判例库），那部分天然可缓存

## 现在的替代做法

- 同一请求内重复调用的 loader 用 React `cache()` 去重（`fetchShellContext` 已如此）
- 每次写入后由页面自行 `router.refresh()`，保证「我刚做的操作立刻可见」
- 性能问题优先用索引与查询收敛解决（见 `drizzle/0013_*` 起的复合索引）
